# Manifest Schema Reference

## JSON Schemas

This knowledge base defines 4 JSON schemas that govern the structure of Witboost template files. All schemas are in `schemas/`.

| Schema | File | Governs |
|--------|------|---------|
| Creation Template | `schemas/template.schema.json` | `template.yaml` — wizard form definition and execution steps |
| Edit Template | `schemas/edit-template.schema.json` | `edit-template.yaml` — fields editable after entity creation |
| Catalog Info | `schemas/catalog-info.schema.json` | `skeleton/catalog-info.yaml` — entity descriptor registered in catalog and sent to tech adapter |
| Parameters | `schemas/parameters.schema.json` | `skeleton/parameters.yaml` — auto-generated by Witboost; template developer only provides `readonly` (components) or `values` (systems) sections with Nunjucks expressions, NEVER hardcoded data |

## How the Files Relate

```
template.yaml
  │
  ├── spec.parameters[]        ← Defines the wizard form (user input)
  │
  ├── spec.steps[]             ← Execution actions after form submission
  │     │
  │     ├── fetch:template     ← Processes skeleton/ files:
  │     │     │                   • Regular files (README, mkdocs, etc.) → Nunjucks RESOLVED
  │     │     │                   • catalog-info.yaml (%SKELETON) → copied AS-IS (expressions preserved)
  │     │     │                   • parameters.yaml → AUTO-GENERATED from user input + step values
  │     │     │
  │     │     └── skeleton/catalog-info.yaml (preserved as Nunjucks template)
  │     │           │
  │     │           ├── ${{ values.useCaseTemplateId }}      ← resolved later via parameters.yaml
  │     │           ├── ${{ values.infrastructureTemplateId }}
  │     │           └── ${{ values.* }}                      ← all expressions preserved
  │     │
  │     ├── publish            ← Commits skeleton (with unresolved catalog-info.yaml) to Git
  │     │
  │     └── catalog:register   ← Registers entity in Witboost catalog
  │
  └── spec.generates           ← Must match skeleton catalog-info.yaml kind

LATER (at display/deploy time):

catalog-info.yaml + parameters.yaml (from Git)
  │
  ├── Witboost renders catalog-info.yaml using parameters.yaml data
  │
  └── Descriptor Assembly
        │
        ├── All spec.mesh.* fields → flattened to root level
        ├── System + all Components → assembled into one YAML
        └── Sent to tech adapter at /v1/validate and /v1/provision
```

## Key Relationships

### `spec.generates` ↔ `catalog-info.yaml kind`

| template.yaml `spec.generates` | catalog-info.yaml `kind` |
|---|----|
| `systemtype:default/dataproduct` | `System` |
| `componenttype:default/outputport` | `Component` |
| `componenttype:default/workload` | `Component` |
| `componenttype:default/storage` | `Component` |
| Custom practice types | `System` or `Component` depending on configuration |

### URN Flow: Template → Skeleton → Descriptor → Tech Adapter

The `useCaseTemplateId` and `infrastructureTemplateId` URNs are defined once in the template's `fetch:template` step values, rendered into `skeleton/catalog-info.yaml`, and ultimately reach the tech adapter in the assembled descriptor:

1. **template.yaml** `spec.steps[].input.values.useCaseTemplateId`: `urn:dmb:utm:my-template:1.0.0`
2. **template.yaml** `spec.steps[].input.values.infrastructureTemplateId`: `urn:dmb:itm:my-provisioner:1`
3. **skeleton/catalog-info.yaml** renders these into `spec.mesh.useCaseTemplateId` and `spec.mesh.infrastructureTemplateId`
4. **Descriptor** flattens `spec.mesh.*` to root level and sends to the tech adapter

### `spec.mesh.specific` — No Fixed Schema

The `specific` section in `catalog-info.yaml` is the primary interface between the template and the tech adapter. Its structure is:

- **Defined by**: the tech adapter's documentation/README
- **Consumed by**: the tech adapter at `/v1/validate` and `/v1/provision`
- **Schema**: `additionalProperties: true` (any key-value pairs the tech adapter expects)
- **Responsibility**: the template developer must read the tech adapter's docs to know what fields to include

The template must collect these fields from the user (via `spec.parameters`) and map them through the `fetch:template` step values into the skeleton's `spec.mesh.specific`.

## Template Types and Corresponding Schemas

### Creation Template (`template.yaml`)

- **apiVersion**: `scaffolder.backstage.io/v1beta3`
- **kind**: `Template`
- **Required in spec**: `generates`, `owner`, `type`, `parameters`, `steps`
- **Schema**: `schemas/template.schema.json`

### Edit Template (`edit-template.yaml`)

- **apiVersion**: `witboost.com/v2`
- **kind**: `EditTemplate`
- **Required in spec**: `owner`, `useCaseTemplateId`, `parameters`
- **No steps** (v2 edit templates handle rendering internally)
- **Schema**: `schemas/edit-template.schema.json`

### Skeleton Catalog Info (`skeleton/catalog-info.yaml`)

- **apiVersion**: `backstage.io/v1alpha1`
- **kind**: `System` or `Component`
- **Required in spec.mesh** (Component): `name`, `description`, `kind`, `version`, `infrastructureTemplateId`, `useCaseTemplateId`
- **Required in spec.mesh** (System): `name`, `version`
- **Schema**: `schemas/catalog-info.schema.json`

### Skeleton Parameters (`skeleton/parameters.yaml`)

- **Sections**: `parameters` (user input), `values` (computed), `readonly` (immutable)
- **Schema**: `schemas/parameters.schema.json`
