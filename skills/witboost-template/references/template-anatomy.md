# Template Anatomy

## Practice Shaper: Terminology Is Not Fixed

Witboost is not limited to Data Mesh. The **Practice Shaper** configures the platform for any data landscape (Data Mesh, Data Lake, BI, ML, etc.). This means:

- "Data Product" might be called "BI Report", "ML Pipeline", "Source System", or anything else
- "Output Port" might be called "Data Contract", "View", "API Endpoint", etc.
- Entity types (`SystemType`, `ComponentType`) are defined in the Practice Shaper and can be fully custom

**Before generating any template, ask the user:**
1. What practice/landscape is configured in Witboost?
2. What are the entity type names used (system types, component types)?
3. What terminology does the organization use?

The default Data Mesh practice uses: Domain → System (Data Product) → Components (Output Port, Workload, Storage).

## Starting Point: Starter Kit

Templates almost always start from the [Witboost Starter Kit](https://github.com/agile-lab-dev/witboost-starter-kit), which is an index linking to 50+ separate template repositories (e.g., `witboost-snowflake-output-port-template`, `witboost-s3-storage-area-template`).

**Before creating a template from scratch, proactively ask the user** (unless they already brought it up):
1. Do you want to start from an existing starter kit template for your technology? If yes, give me the GitHub URL of that specific repository — the starter kit is just an index of 50+ repos, so point me to the one you want rather than having me guess.
2. Do you have an existing template of your own to customize instead?

If the user gives a starter kit URL, fetch and read that repo before generating anything, and use it as the base. If no starter kit or existing template applies, follow the structure below.

## Folder Structure

```
my-template/
├── template.yaml              # Creation wizard: form fields + execution steps
├── edit-template.yaml          # Edit wizard: fields editable after creation (optional)
├── skeleton/                   # Files rendered with Nunjucks and committed to Git
│   ├── catalog-info.yaml       # Entity descriptor (REQUIRED)
│   ├── README.md               # Component documentation
│   ├── mkdocs.yml              # TechDocs configuration
│   └── docs/
│       └── index.md
├── docs/                       # Template usage documentation
│   └── index.md
├── mkdocs.yml                  # Template's own TechDocs config
└── README.md                   # Developer documentation
```

### File Purposes

| File | Purpose |
|------|---------|
| `template.yaml` | Defines the multi-page creation wizard form and the execution steps (fetch skeleton, publish to Git, register in catalog). Schema: `schemas/template.schema.json` |
| `edit-template.yaml` | Defines which fields can be modified after creation. No execution steps in v2. Schema: `schemas/edit-template.schema.json` |
| `skeleton/catalog-info.yaml` | A Nunjucks template (marked with `%SKELETON` on the first line) that defines the entity descriptor. **This file is NOT rendered at template execution time** — it is copied as-is with its Nunjucks expressions preserved. Witboost renders it later using data from `parameters.yaml`. Schema: `schemas/catalog-info.schema.json` |
| `skeleton/parameters.yaml` | Auto-generated by Witboost during template execution. It is not part of a template's skeleton folder. Stores user input and computed values used to render `catalog-info.yaml`. NOT created by the template developer — Witboost generates it from the wizard form data. Schema: `schemas/parameters.schema.json` |

## How Template Execution Works

This is the most important concept to understand. The execution flow has two distinct phases:

### Phase 1: Template Execution (at creation time)

When a user fills the wizard form and submits:

```
User fills wizard form (defined by spec.parameters in template.yaml)
    ↓
Witboost runs the fetch:template step:
    ├── All skeleton files EXCEPT catalog-info.yaml → Nunjucks expressions
    │   are RESOLVED using input.values from the step. The rendered files
    │   are committed to Git. (README.md, mkdocs.yml, docs/, etc.)
    │
    ├── catalog-info.yaml (marked with %SKELETON) → copied AS-IS to Git.
    │   Nunjucks expressions (${{ values.* }}, ${{ parameters.* }}) are
    │   PRESERVED, not resolved. The file remains a template.
    │
    └── parameters.yaml → AUTO-GENERATED by Witboost. Contains:
        ├── parameters: user input from the wizard form
        ├── values: computed values from the step's input.values
        └── readonly: system-managed values (e.g., __system__, __version__)
    ↓
Witboost runs the publish step → commits everything to Git
    ↓
Witboost runs the register step → registers the entity in the catalog
```

### Phase 2: Descriptor Rendering (at display/deploy time)

After creation, whenever Witboost needs to display or deploy the entity:

```
Witboost reads catalog-info.yaml + parameters.yaml from Git
    ↓
Renders catalog-info.yaml using data from parameters.yaml:
    - ${{ parameters.name }} → value from parameters.yaml parameters section
    - ${{ values.description }} → value from parameters.yaml values section
    - ${{ readonly.owner }} → value from parameters.yaml readonly section
    ↓
The rendered descriptor is registered in the catalog
    ↓
On deploy: all descriptors are assembled into one unified descriptor
and sent to the Tech Adapter
```

### Key Implication for Template Developers

Because `catalog-info.yaml` is **not rendered during template execution**, its Nunjucks expressions reference `${{ parameters.* }}` and `${{ values.* }}` — NOT `${{ parameters.fieldName }}` from the template.yaml form. The mapping between the wizard form fields and the skeleton expressions happens through the `fetch:template` step's `input.values`:

```yaml
# template.yaml
spec:
  parameters:
    - title: Metadata
      properties:
        name:                          # wizard form field
          title: Name
          type: string
  steps:
    - id: template
      action: fetch:template
      input:
        values:
          displayName: ${{ parameters.name }}     # maps wizard field → values.displayName
          useCaseTemplateId: urn:dmb:utm:...       # hardcoded value → values.useCaseTemplateId

# skeleton/catalog-info.yaml (NOT rendered — copied as-is)
%SKELETON
kind: Component
spec:
  mesh:
    name: ${{ values.displayName }}               # references values from parameters.yaml
    useCaseTemplateId: ${{ values.useCaseTemplateId }}

# parameters.yaml (AUTO-GENERATED by Witboost)
parameters:
  name: "The value the user typed"
values:
  displayName: ${{ parameters.name }}             # resolves to the user's input
  useCaseTemplateId: urn:dmb:utm:...
```

### The `%SKELETON` Directive

The first line of `skeleton/catalog-info.yaml` MUST be `%SKELETON`. This directive tells Witboost to:
1. Copy the file as-is during template execution (preserve Nunjucks expressions)
2. Auto-generate a `parameters.yaml` file alongside it
3. Render the file dynamically using `parameters.yaml` data whenever the entity needs to be displayed or deployed

Without `%SKELETON`, the file would be treated as a regular skeleton file and its Nunjucks expressions would be resolved at template execution time (legacy behavior).

**`%SKELETON` MUST be the literal first line of the file — byte position 0.** Nothing may precede it, not even a Nunjucks comment (`{# ... #}`) or a `{% set %}` statement. The parser strips the file's YAML content by checking that it starts with `%SKELETON`; anything before it (blank lines, comments, `{% set %}`) causes a `YAMLParseError: Missing directives-end/doc-start indicator line`. Put any `{% set %}` statements needed later in the file on the line(s) immediately **after** `%SKELETON`, and put any explanatory comments **after** `%SKELETON` too (or omit them).

### The parameters.yaml File

The `parameters.yaml` file is **auto-generated** by Witboost — the template developer does NOT create it manually. It has five possible sections:

| Section | Referenced as | Purpose |
|---------|-------------|---------|
| `parameters` | `${{ parameters.* }}` | User input from the wizard form. Editable via the Editor Wizard. |
| `values` | `${{ values.* }}` | Computed/derived values from the `fetch:template` step's `input.values`. For backward compatibility with legacy templates. |
| `readonly` | `${{ readonly.* }}` | System-managed values that cannot be edited by the user. Includes reserved parameters like `__name__`, `__version__`, `__system__`, `__instanceOf__`. |
| `refs` | `${{ refs.* }}` | Values loaded from external sources (repository files, published descriptors) at render time. |
| `environmentParameters` | `${{ env.* }}` | Environment-specific values (e.g., different cluster sizes for dev vs prod). `env.<key>` is an alias for `environmentParameters[environment.id].<key>`. See [Environment Parameters](./environment-parameters.md). |

**Reserved readonly parameters** (auto-managed by Witboost):
- `readonly.__name__` → `metadata.name` (auto-updated on new versions)
- `readonly.__version__` → `spec.mesh.version` (auto-incremented on new releases)
- `readonly.__system__` → `spec.system` (for components: reference to parent system)
- `readonly.__instanceOf__` → `spec.instanceOf` (Practice Shaper type reference)

**Limitation**: Nunjucks expressions in `parameters.yaml` are only resolved for **top-level keys**. Expressions inside nested objects or arrays are not evaluated.

## Tech Adapter ↔ Template Contract

The Tech Adapter receives the **rendered** descriptor (after `catalog-info.yaml` has been rendered with `parameters.yaml` data). The flow is:

```
catalog-info.yaml + parameters.yaml
    ↓ (Witboost renders)
Rendered descriptor
    ↓ (Witboost assembles system + all components)
Unified descriptor YAML
    ↓ (sent to Tech Adapter)
/v1/validate → /v1/provision
    ↓
Tech Adapter extracts fields from spec.mesh.specific
```

### Descriptor Assembly

When Witboost deploys a component, it assembles a **descriptor** containing:
- The parent system's `spec.mesh.*` fields (flattened to root level)
- All components' `spec.mesh.*` fields in a `components` array
- A `componentIdToProvision` field indicating which component to deploy

The tech adapter receives this assembled descriptor and extracts the fields it needs — primarily from `spec.mesh.specific`.

### The `spec.mesh.specific` Section

There is **no fixed schema** for `spec.mesh.specific`. Each tech adapter defines what fields it expects. The contract is implicit — documented in the tech adapter's README or documentation.

**Before generating a skeleton/catalog-info.yaml, you MUST ask the user:**
- What tech adapter will provision this component?
- What fields does the tech adapter expect in `spec.mesh.specific`?

Examples of tech-adapter-specific fields:
- Snowflake Output Port: `{ viewName, tableName, database, schema }`
- S3 Storage Area: `{ bucketName, region, path }`
- Databricks Workload: `{ notebookPath, clusterSpec, schedule }`

### Mock Tech Adapters

Not every component or system requires real infrastructure provisioning. When the user says things like "no deployment needed", "mock tech adapter", "deployment is mocked", or "no infrastructure changes" — the component uses a **mock tech adapter**.

A mock tech adapter is a real, registered microservice that always returns success without performing any actual provisioning. It exists because Witboost requires every component/system to be linked to a tech adapter via `infrastructureTemplateId` — even if nothing needs to be deployed.

Common scenarios for mock tech adapters:
- The component/system is a **metadata-only entity** (e.g., a Data Product system that only organizes components)
- The real infrastructure is managed outside Witboost
- The template is used for prototyping or testing

When using a mock tech adapter:
- `spec.mesh.specific` can be empty (`{}`) or contain only metadata fields
- The `infrastructureTemplateId` still must point to the registered mock tech adapter URN (e.g., `urn:dmb:itm:mock-provisioner:0`)

### URNs Are Always Required

Every template must declare two URNs:

- **`useCaseTemplateId`**: identifies the template itself. Format: `urn:dmb:utm:{name}:{version}`. This is chosen by the template developer.
- **`infrastructureTemplateId`**: links the component/system to the tech adapter microservice invoked at deploy time. Format: `urn:dmb:itm:{name}:{version}`. This must match a registered tech adapter — whether real or mock.

Always ask the user for both URNs. Do not invent them.

## Repository Strategy: Monorepo vs Multi-Repo

Templates must be designed for one of two repository strategies. This choice fundamentally affects how `repoUrl` is constructed and how components discover their parent system's repo.

### Monorepo

All components live in the **same Git repository** as the parent system, each in its own subdirectory (e.g., `./components/my-output-port/`).

**System template responsibilities:**
- Creates the repository
- Injects the repo name into `metadata.annotations` of `skeleton/catalog-info.yaml`, so child component templates can discover it:

```yaml
# System skeleton/catalog-info.yaml
metadata:
  annotations:
    witboost.com/repo-name: ${{ values.repoName }}
```

The annotation key is **provider-agnostic** — always `witboost.com/repo-name`, regardless of whether the repo lives on GitLab, GitHub, Azure DevOps, or BitBucket. Do not use provider-prefixed keys (`gitlab.com/project-slug`, `dev.azure.com/repo-name`, …).

The value is the **repo name only**, not a full URL or an org-qualified slug. It is computed in the system template's `fetch:template` step from the naming convention:

```yaml
values:
  repoName: wit-dp-${{ parameters.domain | replace(r/domain:| |-/, "") }}-${{ parameters.name.split(" ") | join("") | lower }}
```

The org/project/host part is not stored in the annotation — each component template hardcodes it in its own `repoUrl`, since it is a fixed customer-specific detail.

**Component template responsibilities:**
- Reads the parent system's repo name via `EntitySelectionPicker`:

```yaml
dataProductRepo:
  title: Data Product Repository
  type: string
  ui:field: EntitySelectionPicker
  ui:fieldName: dataproduct
  ui:property: metadata.annotations["witboost.com/repo-name"]
  ui:options:
    allowArbitraryValues: false
```

- Uses the parent's repo in the publish step, with a subdirectory `targetPath`. The component decides its own subdirectory: anchor it on `targetPath` with `&rootDirectory` and reuse it in the publish step.

```yaml
steps:
  - id: template
    action: fetch:template
    input:
      url: ./skeleton
      targetPath: &rootDirectory ./components/${{ parameters.name | replace(r/ /, "") | lower }}
      values:
        # ...

  - id: publish
    action: witboostMeshComponent:publish:azure
    input:
      repoUrl: dev.azure.com?organization=my-org&owner=my-project&repo=${{ parameters.dataProductRepo }}
      rootDirectory: *rootDirectory
      parentRef: ${{ parameters.dataproduct }}
```

- Registers via `catalogInfoUrl`, not `repoContentsUrl`. The `repoContentsUrl` variant points at the repo root, which in a monorepo is the *system's* `catalog-info.yaml`, not the component's:

```yaml
  - id: register
    action: catalog:register
    input:
      catalogInfoUrl: ${{ steps.publish.output.catalogInfoUrl }}
```

**Optional: system-imposed root directory.** If the system must dictate where components live (rather than each component choosing `./components/<name>`), the system additionally injects `witboost.com/root-directory` and the component reads it with a second `EntitySelectionPicker` field instead of using the anchor. Prefer the anchor unless the customer explicitly requires this.

### Multi-Repo

Each component gets its **own dedicated Git repository**. The template creates a new repo for each component.

- System and component templates each create their own repo
- No need for repo name annotations in the system's catalog-info.yaml
- `repoUrl` is independent per template (hardcoded or user-selected via `RepoUrlPicker`)
- `targetPath` is typically `.` (root of the new repo)

### Which to Choose

| Aspect | Monorepo | Multi-Repo |
|--------|----------|------------|
| Repo count | 1 per system | 1 per component |
| Component isolation | Shared repo, separate directories | Full isolation |
| System template | Must inject `witboost.com/repo-name` | No extra annotations needed |
| Component template | Reads repo name from parent annotation | Creates its own repo |
| Register step | `catalogInfoUrl` | `repoContentsUrl` |
| CI/CD | Shared pipeline, path-based triggers | Independent pipelines |
| Common pattern | Most customer deployments | Simpler for small projects |

## Wizard Flow

1. **User selects template** from the catalog
2. **Wizard renders form pages** defined in `spec.parameters[]`
3. **User fills required fields** across multiple pages
4. **Steps execute in order** (defined in `spec.steps[]`):
   - `fetch:template` — renders skeleton files with user values via Nunjucks
   - `witboostMeshComponent:publish:{provider}` — commits rendered files to Git
   - `catalog:register` — registers the entity in the Witboost catalog
5. **Output links** are shown (repository URL, catalog entity link)

For detailed documentation on form field types, widgets, arrays, objects, conditionals, and UI directives, see [template-fields.md](template-fields.md).

## Nunjucks Templating

Skeleton files use Nunjucks templating syntax. All values come from the `values` object defined in the `fetch:template` step.

### Variable Interpolation

```nunjucks
${{ values.name }}
${{ values.description | dump }}
${{ values.identifier.split(".")[2] + ".0.0" }}
```

### Conditionals

```nunjucks
{% if values.dependsOn | length > 0 %}
{% for i in values.dependsOn %}
  - ${{ i }}
{% endfor %}
{% else %}[]{% endif %}
```

### Loops

```nunjucks
{% for column in values.schemaColumns %}
  - name: ${{ column.name }}
    dataType: ${{ column.dataType }}
{% endfor %}
```

### Macros

```nunjucks
{% macro renderTag(tag) %}
- tagFQN: ${{ tag }}
  source: Tag
  labelType: Manual
  state: Confirmed
{% endmacro %}
```

### Common Filters

| Filter | Purpose | Example |
|--------|---------|---------|
| `dump` | JSON-safe string output | `${{ values.name \| dump }}` |
| `replace` | String replacement (supports regex) | `${{ values.domain \| replace(r/domain:\| \|-/, "") }}` |
| `lower` | Lowercase | `${{ values.name \| lower }}` |
| `upper` | Uppercase | `${{ values.tableName \| upper }}` |
| `safe` | Prevent escaping | `${{ values.regex \| safe }}` |
| `split` / `join` | String splitting and joining | `${{ values.name.split(" ") \| join("") }}` |

### Computed Variables

```nunjucks
{% set domainNormalized = values.domain | replace(r/domain:| |-/, "") %}
{% set majorVersion = values.identifier.split(".")[2] %}
```

### Skip Templating

Files that should not be processed by Nunjucks (e.g., CI/CD files with conflicting syntax) are listed in the `fetch:template` step:

```yaml
- id: template
  action: fetch:template
  input:
    url: ./skeleton
    copyWithoutRender:
      - .gitlab-ci.yml
      - '*.bin'
```

## File Splitting for Large Templates

Large parameter definitions can be split into separate files using substitution directives:

```yaml
# In template.yaml
spec:
  parameters:
    - title: Schema Definition
      $yaml: ./data_contract_schema.yaml

    - title: From JSON
      $json: ./complex_form.json

    - title: From text
      description:
        $text: ./long_description.txt
```

## Edit Templates

Edit templates allow users to modify existing entities after creation. They use a different API version and kind.

### Key Differences from Creation Templates

| Aspect | Creation Template | Edit Template |
|--------|------------------|---------------|
| `apiVersion` | `scaffolder.backstage.io/v1beta3` | `witboost.com/v2` |
| `kind` | `Template` | `EditTemplate` |
| `spec.steps` | Required (fetch, publish, register) | Not present (v2) |
| `spec.generates` | Required | Not present |
| `spec.useCaseTemplateId` | Not present | Required (array of URNs) |

### Locked Fields

These fields **cannot** be edited after creation and must have `ui:disabled: true` in the edit template:

- Name
- Domain
- Parent system (Data Product or equivalent)
- Identifier
- Development Group

### Structure

```yaml
apiVersion: witboost.com/v2
kind: EditTemplate
metadata:
  name: edit-my-template.1
  title: Edit My Component
  description: Edit an existing component created with My Template
  mesh:
    icon: https://example.com/icon.png
  tags:
    - edit
    - my-component
spec:
  owner: myorg
  useCaseTemplateId:
    - urn:dmb:utm:my-template:1.0.0
  parameters:
    - title: Edit Component
      description: |
        This wizard allows you to edit metadata for your component.
        Name, domain, and identifier cannot be changed.
    - title: Update metadata
      required:
        - description
      properties:
        name:
          title: Name
          type: string
          ui:disabled: true
        description:
          title: Description
          type: string
```

### Best Practices for Edit Templates

- First wizard page should be informational (title + description explaining what can/cannot be changed)
- Include all fields from the creation template, marking non-editable ones with `ui:disabled: true`
- Add a note in non-editable field descriptions (e.g., "Not editable after creation")
- Keep the same field structure so existing values map correctly
